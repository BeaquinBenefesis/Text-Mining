QUESTION ADDRESSED
------------------
What kind of database for the miRNA knowledgebase: relational, graph (Neo4j),
or something else? And how does ontology-aware scoring fit in?


================================================================================
1. DECISION: RELATIONAL (PostgreSQL). NOT NEO4J.
================================================================================

Reasoning — query shape, not data shape, should decide this.

The knowledgebase is bipartite and SINGLE-HOP: miRNA --[co-occurs, score]--> ontology
term. `Association` in models.py is a pair plus a scalar. There is no path of unknown
length to walk. Neo4j earns its cost for variable-depth traversal (MATCH (a)-[*1..5]-(b))
where hop count isn't known in advance. Here it is known: one.

The actual UI queries are all aggregate-and-filter:
  - top-N partners for a miRNA ranked by score  -> indexed lookup + ORDER BY / LIMIT
  - filter by entity type, score threshold, article count, year
  - retrieve supporting sentences/articles for an association -> FK join
  - reverse lookup: all miRNAs annotated to a disease
  - corpus-wide aggregate stats for the evaluation chapter

Every one is a SQL one-liner and a poor fit for Cypher. The confidence score
(AssociationEvidence) is a weighted sum over evidence = an aggregation workload,
which is what graph DBs are worst at.

Supporting practical arguments:
  - Comparable KBs in the domain (HMDD, miRTarBase, DisGeNET) are relational/flat-file.
  - Ecosystem: pandas read_sql, FastAPI + SQLAlchemy, reviewer familiarity.
  - Neo4j adds an operational dependency serving no query the project needs.

WHERE A GRAPH MODEL WOULD HAVE A CASE (for completeness / thesis discussion):
If scope later expanded to INDIRECT INFERENCE — miRNA -> target gene -> pathway ->
disease, proposing associations never observed in one sentence — traversal becomes
central. But that is a different scientific claim needing separate validation, it is
not scoped in thesis_instructions.txt, and even then depth-3 SQL joins are tractable
at this data volume.

INFRASTRUCTURE CAVEAT — the one open decision:
Postgres needs a server process. If no server is available on the institute machine,
SQLite is a legitimate substitute at this scale: same SQL, same schema, closure table
works identically, ships as a single file (nice as a reproducible thesis artifact).
Trade-offs given up: weaker full-text search (FTS5 vs native Postgres FTS), and
concurrent writes — which only matters for the user-feedback loop if several people
annotate simultaneously. Design against SQLAlchemy and the choice stays reversible.


================================================================================
2. TWO TIERS, NOT ONE DATABASE
================================================================================

This matters more than the engine choice.

outputs/mirna/mirna.norm is 15 MB on a TEST corpus. On full PubMed the mention layer
is hundreds of millions of rows. Do not conflate it with what the UI serves.

TIER 1 — MENTION STORE (analytical, append-only, large)
  One row per normalized hit; essentially the current .norm TSV:
  sentence_id, entity_id, entity_type, offsets, raw_text, norm_status, synonym_id.
  Write-once, read-in-bulk, never updated. Consumers: evaluation scripts and the
  aggregation step. NOT the web UI.

  RECOMMENDATION: DuckDB over Parquet, not loaded into Postgres.
    - queries existing TSV/Parquet in place, zero ETL:
        SELECT ... FROM 'outputs/mirna/*.norm'   -- works today
    - columnar; per-entity-type aggregations over 1e8 rows in seconds
    - embedded library, no server
    - analytical layer stays as files under version-controllable paths; reviewers
      reproduce it without provisioning anything

TIER 2 — KNOWLEDGEBASE (served, small, DERIVED)
  Associations, scores, evidence links, entities, synonyms, articles, user feedback.
  Derived from Tier 1 by a rebuild step. Small — bounded by (miRNAs x ontology terms)
  that actually co-occur, orders of magnitude below mention count.

  KEY PAYOFF: Tier 2 can be rebuilt from scratch whenever the scoring function
  changes. And it WILL change — section_weigth() is still a stub, token-distance
  decay is unimplemented. Treating scores as derived rather than authoritative is
  what keeps that cheap.

Notes on three non-obvious choices:

(a) evidence_sentence holds text ONLY for sentences backing an association.
    Do not put the corpus in the database. That is a small fraction of the corpus
    and the only text the UI ever renders. Everything else stays behind the
    IndexedSentenceReader proposed in SENTENCE_READER_DESIGN.md — that design is
    right and remains the corpus access layer.

(b) external_association is SEPARATE from association, not merged at load time.
    Text-mined and curated evidence must stay distinguishable: partly for the
    confidence score (curated agreement should boost it), but critically because
    HMDD overlap is the EVALUATION BASELINE. Merging at load contaminates the
    benchmark. Keep apart, join on demand.

(c) score_version on association — keeps results from multiple scoring
    configurations side by side, needed when the methods chapter has to justify
    the final weighting.

(d) direct_score vs propagated_score kept separate — see section 5.

4. ONTOLOGY SIZES (measured 2026-08-31) AND THE CLOSURE TABLE
================================================================================

Actual counts from /mnt/raidbio2/extproj/.../data/ontologies:

  ncbi_taxonomy.obo            2,854,537 terms    657M
  mondo_disease_ontology.obo      63,267 terms     51M
  gene_ontology.obo               48,340 terms     36M
  cell_ontology_base.obo          18,914 terms     17M
  brenda_tissue_ontology.obo       6,566 terms    2.1M
  pathway_ontology.obo             2,739 terms    1.3M

Taxonomy is 3 orders of magnitude larger than everything else. Full taxonomy closure
would be ~2.85M x mean depth = 50-70M rows. Everything else combined is ~140k terms;
at mean ancestor count ~20-25 for multi-parent DAGs that is ~3M closure rows, a couple
hundred MB — trivial for Postgres.

RESOLUTION — taxonomy is excluded from the closure, for a SEMANTIC reason:

  Taxon is not an annotation dimension. NormalizationContext.get_taxon_relevance()
  uses taxon hits as DISAMBIGUATION CONTEXT for miRNA normalization (which organism,
  so mir-21 resolves to the right prefix). It is a qualifier on an association, not
  an association target.

  Propagation up the taxonomic tree yields nothing: miR-21 -- Homo sapiens rolls up
  to Hominidae, Primates, Mammalia, Eukaryota. Every association in the corpus
  terminates at "associated with Eukaryota". No annotation content.

  WHAT TO DO INSTEAD: a curated ROLLUP TABLE mapping each observed taxon to its
  nearest ancestor in a small curated rank set — human, mouse, rat, common model
  organisms, plant vs. animal (relevant given the plant/animal miRNA naming
  convention bug already fixed in normalization.py). ~30 rows. Not a closure.

FURTHER PRUNING — closure over OBSERVED terms only:
  Only terms that actually receive a hit in the corpus need closure entries, plus
  their ancestors. Realistically 10-20k MONDO terms, not 63k.
  OntologyGraph.ancestor_closure() (ontology.py:266) already computes exactly the
  induced subgraph over a set of observed indices plus ancestors. Build the closure
  table from that, not from the whole OBO.

  Also: follow only is_a. Already the case — relationship='is_a', _rel_subgraph.
  [AMENDED 2026-09-15, section 15.1: the relationship set is per ontology. BTO
   follows is_a + part_of; every other ontology stays is_a only.]


================================================================================
5. EVIDENCE PROPAGATION UP THE DAG  (main technical result of the session)
================================================================================

5.1 TWO DIFFERENT THINGS, DO NOT CONFLATE
-----------------------------------------
(a) QUERY EXPANSION — retrieval-side, at QUERY TIME, does not touch the score.
    User searches "carcinoma"; UI joins closure to also surface subtype
    associations. Nearly free. Implement regardless — it is what makes the UI
    filter behave sensibly.

(b) EVIDENCE PROPAGATION — scoring-side, PRECOMPUTED, changes the score.
    Aggregates subtype evidence into an ancestor-level association, so a miRNA
    hitting 30 different carcinoma subtypes gets a real `carcinoma` association
    even if no sentence ever says "carcinoma".
    THIS is what belongs in analysis.py.

Both are wanted. Only (b) is precomputed.


5.2 THE CONSTRAINT: PROPAGATE *BEFORE* THE PER-ARTICLE LOG
----------------------------------------------------------
AssociationEvidence currently does:

    per article:  article_sum = SUM section_weight(section)
    on flush:     corpus_sum += log2(1 + article_sum)
    final:        log2(1 + corpus_sum)

The per-article log2 is a SATURATION function — it stops one paper saying
"miR-21 / breast cancer" fifty times from dominating. That damping is lost if
propagation happens at the wrong layer.

FAILURE MODE IF DONE POST-HOC (summing final descendant scores into the ancestor):
  An article mentioning `breast carcinoma`, `lung carcinoma` and `carcinoma`
  contributes three separately-log-compressed terms to the carcinoma score.
  Compression applied per-subtype, then summed linearly => broad terms inflate in
  proportion to how many subtypes happen to co-occur. Systematic bias toward the
  LEAST informative terms. Would show up in evaluation as high-level MONDO terms
  topping every ranking. This is a real methodological flaw, not a tuning issue.

CORRECT PLACEMENT: propagated weight must land in the ANCESTOR association's open
article bucket (_current_article_sum) before that bucket is flushed, so all of one
article's direct and propagated contributions are compressed together.

[REVISED 2026-09-13 -- the original "minimal change" (extra CoOccurences with a
 decayed weight, yielded from Grouper) and the per-article EFFICIENCY NOTE are both
 withdrawn. Reasons below.]

DESIGN OF RECORD: per co-occurrence, direct call, no synthetic CoOccurences.
  For each direct CoOccurence recorded by EvidenceAggregator:
    - record it on the direct (mir, term) association as before;
    - for each cached ancestor A of term (OntologyGraph closure, is_a only):
        ancestor_assoc.record_propagated(epoch, article_id,
                                         cooc.score * decay(term -> A))
  AssociationEvidence.record_propagated shares the epoch check and lazy flush of
  record_cooccurrence, so the contribution joins the ancestor's bucket for that
  article. EvidenceAggregator holds NO article-boundary state.

WHY NOT SYNTHETIC CoOccurences (inferred flag or not):
  write_cooccurrences_tsv is a pass-through between Grouper and the aggregator
  (pipeline.py), and db/loaders/corpus.py builds association_evidence from .cooc.
  Synthetic rows would multiply .cooc (~31M -> ~180M rows) and give propagated
  associations "evidence" sentences that do not contain the ancestor term, with
  spans that do not exist. A CoOccurence records an observation at a location in
  text; a propagated contribution has no location. Keep it out of that type.

WHY NOT BUFFER PER ARTICLE (the withdrawn efficiency note):
  Equivalent result, since decay is linear in the per-co-occurrence score
  (see CONSTRAINT below). Measured saving is small: on a 4,000-article sample,
  per-co-occurrence expansion made 366,756 propagation calls vs 125,006 per
  (article, mir, term) -- about 3x. At ~0.2 us/call that is ~1 min over the full
  disease run (~140M calls), against a 91s .norm scan alone. It would also add
  three failure modes the per-co-occurrence form does not have:
    - read-then-write ordering (a touched term that is also an ancestor of another
      touched term gets its propagated weight propagated again);
    - coupling to AssociationEvidence's lazy flush timing;
    - an explicit end-of-stream flush (the `pending` term in score only rescues
      the last article's in-bucket sum; per-co-occurrence already puts propagated
      weight there).

IMPLEMENTATION REQUIREMENTS:
  - Iterate the CLOSURE, not parent-by-parent. The IC ratio telescopes along one
    path, but an ancestor reachable by k paths in a multi-parent DAG would receive
    k contributions.
  - Cache decay(term -> A) with the ancestor list: one lookup in the hot loop, not
    two IC lookups and a division.
  - Skip ancestors with decay 0 (the root, IC = 0) or below a floor. Saves calls
    and avoids creating associations that can only score 0 (cf. 12.4 root junk,
    8.3 sizing warning).
  - Do NOT use dict.setdefault(key, Association(...)) on this path: it constructs
    an Association per call even when the key exists. Measured 0.62 us/call vs
    0.18 us for get + record_propagated. Same issue on the existing direct path.
  - New ancestor associations take entity_types (MIR, term_type) from the source.

CONSTRAINT THIS PLACEMENT COMMITS TO (state it in the methods chapter):
  Propagation must be a LINEAR map: the ancestor's contribution is a fixed scalar
  multiple of each direct contribution, the scalar depending only on (term, A).
  Per-co-occurrence factors (section weight, a future token-distance decay) are
  fine -- they are inside cooc.score. Not expressible here: article-level rules
  such as MAX over descendants instead of SUM, or conditioning on how many
  distinct subtypes an article hit. Sentence-context rules (e.g. suppress
  propagation to A in a sentence that names A directly) remain expressible --
  a sentence's co-occurrences arrive adjacently -- at the cost of a per-sentence
  buffer.

DIRECT vs COMBINED SCORE: one accumulator, one score column. "Attested vs
inferred" is answered by association_evidence rows / n_articles_direct, not by a
second score. The direct-only HMDD ablation is a second build with propagation
off, consistent with 8.2's one-scoring-config-per-file; record the propagation
flag and ontology snapshot in build provenance so the two files are distinguishable.
If both scores are ever wanted in one file, they need two accumulators:
log2(1+d) + log2(1+p) != log2(1+d+p). [Supersedes the split in 5.4 and 8.3.]


5.3 DECAY FUNCTION: IC RATIO, NOT HOP DISTANCE
----------------------------------------------
Do NOT use exp(-distance). Hop count is not comparable across ontology branches;
MONDO granularity is very uneven, so 3 hops in one subtree is a much larger
specificity drop than 3 hops in another.

Use:
    decay(term -> ancestor) = IC(ancestor) / IC(term)

_descendant_count_cache (ontology.py:304) is exactly what IC derives from, and this
connects to work already done in analysis/analyze_mir_ic.ipynb.

Three reasons this is better:
  1. Calibrated to actual specificity loss, not tree topology.
  2. In [0,1] by construction, composes cleanly with section weights.
  3. The ROOT gets IC=0 hence weight 0 — vacuous associations like
     "miR-21 -- disease" fall out to zero automatically, with NO arbitrary depth
     cutoff to justify in the methods chapter. Much cleaner to defend.


5.4 SCHEMA CONSEQUENCE
----------------------
Keep direct and propagated evidence separable (see section 3 schema):
  direct_score, propagated_score, n_articles_direct, n_articles_propagated

A reviewer will ask whether an association is directly attested in text or only
inferred by rollup. The direct-only scores are also needed as an ABLATION when
benchmarking against HMDD. Storing only the combined score throws that away and
would require re-running the pipeline to recover.

6. SUMMARY OF DECISIONS (as of 2026-08-31; amended by section 8)
================================================================================
  - Tier 2 KB: PostgreSQL (SQLite acceptable fallback if no server).
  - Tier 1 mentions: DuckDB over Parquet/TSV, queried in place, no ETL.
  - Closure table for MONDO, GO-BP, CL, BTO, PW — built over OBSERVED terms via
    OntologyGraph.ancestor_closure(), not full OBO files.
  - Taxonomy: small curated rollup table, NO closure, NO propagation.
  - Propagation precomputed in analysis.py at article-flush time, IC-ratio decay,
    injected BEFORE the per-article log.
  - Query-time closure joins serve retrieval expansion only.
  - Corpus text stays on disk behind IndexedSentenceReader; only evidence
    sentences go in the DB.

8. REVISED DESIGN -- 2026-09-03 (DESIGN OF RECORD)
================================================================================

Supersedes the Tier-1/Tier-2 split of section 2 and the schema sketch of section 3.
The rationale in sections 4 and 5 (closure over observed terms, taxonomy excluded,
IC-ratio propagation before the per-article log) is unchanged and still governs.

MEASURED SCALE that motivates this (full-corpus run, outputs/mirna_and_disease):
  .hits   9.6 GB
  .norm  12.0 GB
  .cooc   2.7 GB   31,410,695 co-occurrence rows
  .assoc   67 MB    1,482,996 association rows
The four-order-of-magnitude gap between co-occurrences and associations is the
whole argument for splitting the files.


8.1 TWO SQLITE FILES, JOINED VIA ATTACH  [DEFERRED -- see section 9]
---------------------------------------
  atlas_core.db      -- small, served, ships as the thesis artifact.
  atlas_evidence.db  -- large, deferred, built from the hit shards on disk only
                        when mention-level drill-down is wanted.

Both opened read-only (`file:...?mode=ro&immutable=1`; immutable is a promise, safe
because each file is built once and never updated). No cross-file foreign keys --
SQLite cannot express them across ATTACH. Integrity is enforced by a validation
script after build (8.5).

Engine: raw SQL DDL in versioned .sql files + stdlib sqlite3. NOT SQLAlchemy.
Reason: ATTACH, immutable=1 and read-only file shipping are SQLite-specific and
load-bearing, so the portability SQLAlchemy was protecting has already been given
up; keeping the ORM would only obscure the DDL. Use STRICT tables (SQLite 3.53.2
on this machine) to recover the type checking the ORM would have given.

Bulk loading goes through duckdb's sqlite extension, not through Python:
    INSTALL sqlite; LOAD sqlite;
    ATTACH 'atlas_core.db' AS core (TYPE SQLITE);
    INSERT INTO core.association SELECT ... FROM read_csv('*.assoc', ...);
Verified working here. This keeps 31M evidence rows out of the Python heap.
Python's remaining jobs: DDL, entity-id minting, validation.


8.2 BUILD IDENTITY -- THE PRICE OF DROPPING FOREIGN KEYS
--------------------------------------------------------
atlas_evidence.db stores integer entity ids MINTED BY THE CORE BUILD. Rebuild core
with one extra ontology term and those ids can shift; attaching a stale evidence
file then produces joins that succeed and return nonsense. That is strictly worse
than a missing FK, which at least fails loudly.

  build_meta(build_id, schema_version, built_at, source_run, score_config)

One row, in BOTH files. The connect helper REFUSES to attach a pair whose build_id
differs. This is the one check that must run at open time, not merely in the
validator.

build_meta also replaces the per-row `score_version` column proposed in section 3(c):
one scoring configuration per file, since both tiers are drop-and-recreate.


8.3 CORE TIER
-------------
Entity -- UNIFIED for miRNAs and ontology terms. Deliberate single-table
inheritance: type-specific columns (organism, reference_level) are NULL for MONDO
terms, source_ontology is NULL for miRNAs. Accepted, because it makes `association`
have a single FK target and lets the UI stay generic over entity types. Splitting
out an entity_mirna side table would be cleaner in the abstract and buys nothing
for six columns.

  entity(id INTEGER PK,              -- surrogate; the join key everywhere
         accession TEXT UNIQUE,      -- MIMAT0000062, MONDO_0007254
         entity_type,                -- HitType
         name,
         source,                     -- mirbase / mondo / go / cl / bto / pw
         is_obsolete, replaced_by,
         reference_level,            -- mature | precursor | family; miRNA only
         organism,                   -- miRNA only
         ic_structural,              -- descendant-count IC, ontology.py:304
         ic_corpus,                  -- corpus-frequency IC
         n_articles_corpus)          -- the count ic_corpus derives from

  Integer surrogate ids, not accession strings, as the key: 1.48M association rows
  index on two of them.

  TWO IC COLUMNS, not one. They measure different things and the plan already
  commits to comparing them as an evaluation-chapter result -- one column cannot.
  CORRECTNESS CONSTRAINT on ic_corpus: article counts MUST be propagated up the
  closure before the log (a hit on `breast carcinoma` counts toward `carcinoma`).
  Raw direct frequency is not IC; terms with zero direct mentions but many
  mentioned descendants would otherwise be undefined.

  synonym(entity_id, surface_form, synonym_type)     -- input to syngrep
  ontology_closure(ancestor_id, descendant_id, min_distance)

  min_distance, NOT distance: in a multi-parent DAG several paths exist and the
  distance is not unique. Minimum is the convention. Kept for display and
  debugging only -- propagation decay uses the IC ratio (section 5.3), not hops.

  article(id INTEGER PK, pmid, pmcid, year, journal, corpus_source, citation_count)
  -- year/journal/citation_count currently have no data source; see 8.6.

  association(id INTEGER PK,
              mirna_entity_id, term_entity_id, term_type,
              n_sentences,
              n_articles_direct, n_articles_propagated,
              first_year,
              score_direct, score_propagated, score_norm,
              UNIQUE(mirna_entity_id, term_entity_id))

  Score components as columns so rescoring is an UPDATE.

  DIRECT vs PROPAGATED IS KEPT (section 5.4), and is a different axis from
  raw vs normalised. score_raw/score_norm alone would discard: (i) the direct-only
  ablation needed for the HMDD benchmark, and (ii) the answer to "is this
  association attested in a sentence, or only inferred by rollup?", which a
  reviewer will ask. Recovering either would mean re-running the pipeline.

  term_type is denormalised from entity.entity_type -- justified, it is in the hot
  filter path, but it is a duplicated fact and the validator must check agreement.

  external_association(source, mirna_entity_id, term_entity_id, source_evidence)
  -- HMDD etc. Separate from association, never merged at load (section 3b).

  mention_timeline(mirna_entity_id, year, n_articles)
  association_timeline(assoc_id, year, n_articles)
  -- Count ARTICLES, not mentions. Blocked on 8.6; define the tables, ship empty.

  Indexes: association(mirna_entity_id), association(term_entity_id),
           association(score_norm), entity(accession), ontology_closure(ancestor_id).

  SIZING WARNING: 1.48M direct associations is comfortably "small". Ancestor
  propagation multiplies it ~10-20x (15-30M rows) and the core file stops being
  something to ship as a resource. Plan a prune-at-load threshold: drop propagated
  associations below a score floor, and drop ancestors below an ic_structural
  floor. The root already falls out at zero weight by construction (section 5.3).


8.4 EVIDENCE TIER
-----------------
  sentence(id INTEGER PK, article_id, section_num, sentence_num)   -- NO text column
  normalized_hit(id INTEGER PK, sentence_id, entity_id,
                 start_position, hit_length, raw_text,
                 norm_status, target_type, dead)
  association_evidence(assoc_id, mirna_hit_id, term_hit_id)

TEXT IS NOT STORED. 31.4M co-occurrences span order 1e7 distinct sentences; their
text is tens of GB, and it would be the single largest thing in the design.
ArticleReader (article_utils.py:58) already mmaps the .sent files behind a
byte-offset index -- that IS the sentence store. Resolve text at render time
through it. This keeps section 3(a)'s conclusion rather than reversing it.

NORMALIZATION STATUS IS THREE COLUMNS, NOT ONE FUSED ENUM. The code has three
orthogonal fields and they must be stored as they are:
  norm_status   -- NormalizationStatus: NORMALIZED | FALLBACK | UNKNOWN_ENTITY
                                        | FILTERED | IN_BLACKLIST
  target_type   -- NormalizationTargetType: MIR_FAMILY | MIR_PRECURSOR | MIR_MATURE
  dead          -- bool
A single fused enum (MAPPED_TO_MATURE / AMBIGUOUS_TYPE / NOT_IN_MIRBASE / FAILURE
/ DEAD) loses information and would drift from enums.py.

association_evidence referencing HIT rows rather than sentence rows is right:
spans, status and section come along for free, and the synonym-feedback loop needs
to reach hits that FAILED normalization -- which are rows here, not associations.


8.5 VALIDATION SCRIPT (replaces the foreign keys)
-------------------------------------------------
Runs after every build, over the ATTACHed pair. Must check at minimum:
  - build_id agreement between the two files
  - no orphan entity_id in association, external_association, normalized_hit
  - no orphan assoc_id / hit_id in association_evidence
  - association.term_type agrees with entity.entity_type (denormalisation check)
  - UNIQUE(mirna_entity_id, term_entity_id) actually holds
  - closure is acyclic, has no self-pairs, min_distance >= 1
  - score columns in range; score_direct <= score_norm where both present
  - row counts reconcile against the .assoc / .cooc source files
A build whose validation fails is not published. Cheap, and it is the only thing
standing where the FKs used to.


8.6 BLOCKER: ARTICLE METADATA HAS NO SOURCE
-------------------------------------------
The corpus is `sentence_id \t text` and nothing else. ArticleMetadata
(article_utils.py:20) carries only article_id. Therefore article.year, .journal,
.citation_count and BOTH timeline tables have no input today.

Filling them needs a bulk PubMed metadata fetch over ~650k PMIDs
(scripts/pubtator.py is the nearest existing hook). That is its own work item.

DECISION: ship v1 with article(pmid) only. Define year/journal/timeline structures
in the DDL and leave them empty. Do not let metadata acquisition delay the first
.db file -- the timeline features are additive, the association table is not.


8.7 WHERE THE CODE LIVES
------------------------

9. AMENDMENT -- 2026-09-03(b): SINGLE FILE FIRST (CURRENT DESIGN OF RECORD)
================================================================================

Same day as section 8, later discussion. Amends 8.1, 8.2, 8.5, 8.7 and the file
count in 8.8. Everything else in section 8 (entity/association/closure shapes,
the IC columns, the direct/propagated score split, no-sentence-text, the three
normalization columns) is UNCHANGED -- this amendment is about file count only.

TRIGGER: re-examining why the sentence text argument was raised as a reason to
reconsider the split, and finding it was never actually the reason for the split
in the first place. Section 8.4 already commits to NOT storing sentence text
regardless of file count -- ArticleReader's mmap index is the sentence store
either way. So "I read sentences from disk either way" is true, but it doesn't
bear on the one-file-vs-two question at all; raising it just prompted a look at
what the split was actually buying, and whether that was needed yet.

What the split actually bought: a small atlas_core.db shippable as a standalone
thesis artifact, decoupled from the ~31M-row evidence tables. That is a real
tradeoff, but it is an optimisation for a requirement that is not yet confirmed
(a downloadable resource file is a documentation/deliverable question for the
supervisor, not an engineering one) and not yet costed (Stage 3e, which is the
first point evidence-tier row counts get measured, has not been reached).


9.1 DECISION
------------
Build ONE file, e.g. atlas.db, containing every table from 8.3 AND 8.4 together
(entity, synonym, ontology_closure, article, association, external_association,
timelines, sentence, normalized_hit, association_evidence). Section 3a-3d of the
implementation plan (core only) and 3e (evidence tier) become phases of loading
the SAME file, not separate files.

REASONS, in order of weight:

  1. You do not need to decide the file-count question now. The evidence tier
     (3e) was already deferred behind a working core; one file is what "core
     first" produces by default when there is no second file to defer INTO.
     The two-file question can only be answered with real evidence-tier row
     counts, which do not exist until 3e is attempted.

  2. SQLite enforces foreign keys directly, in one file. `PRAGMA foreign_keys =
     ON` turns every `REFERENCES` clause into a real constraint checked at
     INSERT time. This is strictly better than section 8.5's validation script,
     which only exists because ATTACH cannot express a foreign key across
     files. One file recovers a real integrity mechanism instead of a
     post-hoc check that runs after the damage is already written.

  3. It is a reversible decision, not a one-way door. If normalized_hit /
     association_evidence later prove too large to ship in the same file as
     the small tables, splitting them out is a mechanical migration -- copy
     two tables into a second file, repoint the loader, drop them from the
     first -- not a schema redesign. This is exactly why 8.7's schema.sql
     should stay organised by tier internally (see 9.3) even though it is one
     file: the split, if it comes, should cost an afternoon, not a rewrite.

  4. Load order becomes a hard, enforced constraint rather than a convention.
     entity must be fully populated before association (FK to entity), which
     must exist before association_evidence (FK to both association and
     normalized_hit). With PRAGMA foreign_keys=ON this order is not optional
     -- SQLite rejects an out-of-order insert outright, which is the correct
     failure mode. The loader sequencing described in 8.7 is unchanged; it is
     now enforced by the database instead of only by discipline.


9.2 WHAT THIS REMOVES FROM SECTION 8
-------------------------------------
  - ATTACH between files: gone, not needed within one file.
  - build_meta's cross-file role (8.2): gone. Keep ONE build_meta row per file
    for provenance (build_id, schema_version, built_at, source_run,
    score_config) -- still useful for "which run produced this .db", just no
    longer load-bearing for a build_id MATCH check, since there is only one
    file to match against itself.
  - The validation script's job (8.5) shrinks to what FK constraints cannot
    express: term_type agreeing with entity.entity_type (denormalisation,
    9.3), UNIQUE(mirna_entity_id, term_entity_id) holding, closure acyclicity,
    score ranges, row counts reconciled against source files. Orphan-id checks
    (the majority of the old list) are now redundant with PRAGMA
    foreign_keys=ON and can be dropped from the script.
  - `immutable=1` / read-only-by-default framing (8.1): still correct practice
    for a build-then-serve file, just no longer solving a cross-file integrity
    problem -- it is solving "don't let a stray notebook INSERT corrupt the
    shipped file" (see analysis/sqlite_tutorial.ipynb section 6), which
    applies identically to one file or two.

10. AMENDMENT -- 2026-09: STAGE 3 BUILT, SEVERAL 8/9 DECISIONS REVERSED
================================================================================

10.1 SENTENCE TEXT IS STORED AFTER ALL -- reverses 8.4 / 9's "no text, resolve
via ArticleReader" stance.

Byte-offset caching (the alternative considered) is fragile: any corpus
mutation after build time makes a cached offset return the wrong sentence
silently. That risk was already implicit in every stored hit position, just
not visible until byte offsets made it concrete.

The volume argument against text no longer holds at the real scope. §8.4's
"tens of GB" estimate was for text behind all 31.4M co-occurrences, TAXON
included, undeduplicated. The real requirement is distinct sentences backing
DISEASE associations only (TAXON is context, never an association target --
unchanged from 8.3): measured 1,985,435 distinct sentences behind 20,259,783
DISEASE co-occurrence rows, ~156 bytes/sentence average -> ~300-400MB. Storing
text removes ArticleReader as a query-time dependency entirely -- no
byte_start/byte_length columns, no mmap lookups at render time.

  sentence(id INTEGER PK, article_id, section_num, sentence_num, sentence_text)

10.2 normalized_hit DROPPED. association_evidence carries positions inline.

With the synonym-feedback use case (reaching failed-normalization hits) no
longer a near-term priority, the only remaining job of a generic hits table
was supplying spans to association_evidence -- so that indirection is gone:

  association_evidence(id, association_id, sentence_id,
                        mirna_start, mirna_end, term_start, term_end)

norm_status is not a column: every row here passed normalized_successfully()
upstream (Grouper.extract_valid_combinations), so it is constant
(NORMALIZED|FALLBACK) by construction -- storing it would be storing a
constant. dead was considered and kept out for the same reason it turned out
not to apply here as cleanly hoped: worth revisiting only if a concrete need
for it on evidence rows shows up.

10.3 ENTITIES_PER_SENTENCE_CAP = 20 (analysis.py), counted by DISTINCT SPANS.

Some corpus "sentences" are mis-segmented tables (a review's table dumped as
one line) that blow up combinations() -- one measured case had 2,583 distinct
miRNA mentions x ~80 repeated disease positions = 206,640 co-occurrence rows
from a single sentence. Grouper.extract_cooccurrences now skips any sentence
whose hit count exceeds the cap before calling extract_valid_combinations.

Critically, the cap counts DISTINCT (start, length) SPANS, not raw hit rows.
Reason: MirNormalizer resolves a species-ambiguous bare mention (no prefix,
multiple surviving taxon candidates) into one NormalizedHit PER candidate
species at the SAME span -- measured 17.8% of all MIR mention spans in the
full corpus affected. Counting raw rows would flag ordinary multi-organism
prose (common in miRNA literature) as false-positive "tables." A family-level
fallback was considered and rejected: only ~23% of precursor rows (~7% of
distinct bodies) have any family mapping, so it wouldn't have generalized.
Sampled real sentences (30 per bucket, in outputs/sentence_hit_examples/)
confirm the cutoff: 6-20 spans is uniformly genuine prose; 21-50 is a mix
tipping toward tables; 51-100 was 100% table/list artifacts in-sample.

10.4 corpus.py LOADS article + sentence + association_evidence IN ONE PASS.

Not three separate loaders. Reason: EvidenceAggregator (models.py) folds each
CoOccurence's score into a running per-article sum and discards the object
immediately -- by the time an Association has a final score, no individual
co-occurrence (sentence, positions) survives to build evidence rows from.
association_evidence therefore cannot be built from a downstream DB query
(association has no sentence-level columns, deliberately -- 8.3) or from
post-aggregation objects. It has to consume the .cooc file directly, which
already persists exactly what's needed per co-occurrence (this is what
write_cooccurrences_tsv was already doing, before Stage 3 needed it for this
reason). CoOccurence gained one field to make this work: origin_file_name
(which corpus .sent file an article lives in -- needed for MultiArticleReader,
was on NormalizedHit already but wasn't threaded through to CoOccurence).

Consequence: any .cooc file written before this change (missing
origin_file_name, predating the entities-per-sentence cap) is stale and must
be regenerated before the evidence tier can be built from it.

10.5 article METADATA -- real source found, §8.6 gap partly closed.

/mnt/raidbio2/extdata/textmining/master/{pubmed_metadata.csv,pmc_metadata.csv}
(PMID/PMCID, DOI, Title, Journal, PubDate, PubType, Authors, AuthorsCount).
Well-formed RFC4180 CSV (comma-containing fields are quoted) -- a naive split
breaks on it, a real CSV parser doesn't. One gotcha: pmc_metadata.csv has a
field (a large-consortium paper's Authors list) over Python's default 128KB
csv field limit; needs csv.field_size_limit(sys.maxsize) or it crashes.

  article(id, external_id, year, journal)

Both year and journal are nullable, measured against the real files, not
assumed: PubDate is empty for 12.6% of pubmed_metadata.csv rows and 16.4% of
pmc_metadata.csv rows (of the rest, format is YYYY-MM-DD, with a small
PMC-side fraction as YYYY-MM/YYYY -- still year-extractable). journal is
non-empty in pubmed_metadata.csv but empty for a small fraction of
pmc_metadata.csv rows. title/DOI/PubType/Authors/AuthorsCount not carried --
no named feature needs them yet.

mention_timeline / association_timeline (8.3) are still NOT built -- the
article.year gap that blocked them is closed, but they remain derived
aggregate tables (COUNT DISTINCT article per (entity_or_assoc, year), joined
through association_evidence -> sentence -> article) to be computed after a
build, not loaded from an external source. Own work item.

10.6 build_db.py is the one runner (9.3's scripts/db/build_db.py, actually
written): opens the DB, loads the ontology graphs, then inside one `with
MultiArticleReader(...) as reader, con:` block runs entity -> synonym ->
association -> corpus (article/sentence/association_evidence together, 10.4)
-> ontology_closure -> article_metadata, in that order. association before
ontology_closure and corpus because both derive from it (ontology_closure's
observed-term set is `SELECT DISTINCT term_entity_id FROM association`;
corpus resolves each co-occurrence's association_id against it).

11. AMENDMENT -- 2026-09-09: USER INTERFACE, AND WHAT BUILDING IT CHANGED
================================================================================

Scope: the "user interface" work package. Adds the mention layer, miRBase name
history and search index to the schema of section 8.3/10, and records five
findings from querying the built atlas.db that changed the design. Everything in
sections 9 and 10 stands.

11.1 THE CORPUS IS 99% POST-2010 -- TIMELINES MUST BE NORMALISED
----------------------------------------------------------------
Measured over article.year: pre-2010 is 2,499 articles (1.0%), 2020+ is 45.7%.

A raw per-year mention count therefore measures corpus coverage, not research
activity. Measured on the 20 most-associated human miRNAs, the raw curve peaks
in 2021 or 2022 for 20 of 20 -- every miRNA appears to be "currently trending"
because the corpus is. Dividing by that year's article total disperses the peaks
across 1998-2025 (5 of 20 at 2021+), which matches the actual history of the
field: early let-7/lin-4 work, then the 2013 boom.

DECISION: share = n_articles(mir, year) / n_articles_corpus(year) is the default
series everywhere and the quantity the research score is built from. Raw counts
stay visible as context bars so sample size is never hidden. corpus_year holds
the denominator.

CONSEQUENCE FOR THE RESEARCH SCORE: its volume term sums yearly shares, not
articles, and it deliberately has NO recency component -- the corpus is already
recency-biased and a recency term would double-count that. Weights are
provisional; validate against HMDD entry count per miRNA (Stage 5) before
reporting the score as a result. It measures attention, not characterisation.

11.2 THE MENTION LAYER IS BACK, AT PAIR GRANULARITY
----------------------------------------------------
association_evidence only covers sentences where a miRNA co-occurred with an
ontology term, so a timeline derived from it answers "how often was this miRNA
annotated", not "how often was it mentioned". Methodology, target-validation and
biomarker papers naming no partner term in the same sentence vanish.

  mir_mention_article(mir_key, article_id, blacklisted)     3,694,133 rows

Measured cost: one duckdb pass over the 19GB .norm, 92s end to end (91s of it
the raw scan; the aggregation is ~1s). Three granularities were considered --
counts only (240,754 rows), (mir, article) pairs, and full mentions with
positions (19.4M rows). Pairs won: counts alone give a chart that cannot be
clicked through to the articles behind a bar, and full mentions roughly double
the file for flexibility rather than a named feature. Counts derive from pairs
with a GROUP BY, so nothing is lost.

mir_key is TEXT and NOT a foreign key to entity, deliberately: blacklisted hits
normalise to no accession, and carrying them is the point (11.3).

SIDE EFFECT: mentions span 320,963 articles against the 273,702 the corpus
loader created. The missing 46,963 are inserted before article_metadata runs, so
the metadata pass backfills them too -- articles with a year rose from 240,539
to 281,435.

11.3 AMBIGUOUS miRBASE IDENTIFIERS ARE SURFACED, NOT RESOLVED
--------------------------------------------------------------
MirNormalizer marks a mention IN_BLACKLIST when its name has been carried by
more than one accession across releases, and returns normalized_id = None. Those
hits never become co-occurrences, so they were absent from the database entirely.

The aggregate looks negligible and the distribution is not: IN_BLACKLIST is
140,614 of 38,599,130 MIR hits (0.36%), but the top 20 names carry 79% of it,
and they are not obscure -- hsa-mir-378 (13,512 hits) and hsa-mir-34b (12,578)
alone are 18.6%. A reader searching miR-34b would silently get nothing.

RESOLUTION WAS CONSIDERED AND REJECTED. The release history dates the switchover
exactly (hsa-miR-34b was MIMAT0000685 through v9_2, MIMAT0004676 from v10), and
article.year now exists, so mentions could in principle be assigned by
publication date. But publication year dates the PAPER, not the annotation its
authors were working from: pipelines lag releases and reviews inherit legacy
names from their sources. It would be a guess with no bound on its error, which
is not something a knowledgebase should do silently.

INSTEAD: /name/{name} shows the release history, the candidate accessions, and
the mention timeline for the surface form -- the one place these mentions are
visible. Resolution stays out.

11.4 THE miRBASE HISTORY TABLES CLOSE TWO OPEN ITEMS
-----------------------------------------------------
mirna_mature_history.tsv / mirna_precursor_history.tsv (544,564 rows combined:
mirna_name, accession, version, dead, new_name) are a superset of the
*_id_conflicts.tsv files -- conflicted names are exactly those mapping to more
than one accession, verified SET-IDENTICAL to the normalizer's actual blacklist
(218 distinct lowercase names). The conflict files are no longer needed as an
input, which also sidesteps the duplicated header row both of them carry (it puts
the literal string "mirna_name" into ambiguous_mature / ambiguous_precursors).

  (a) miRNA SYNONYMS, previously "no literal source identified" -- mir_regex.syn
      is patterns, not surface forms. The history names ARE literal surface
      forms: 8,421 of 49,440 mature and 1,329 of 39,314 precursor accessions
      have carried more than one name. 9,970 legacy synonyms loaded, so
      'hsa-miR-34b*' now finds MIMAT0000685. The 218 ambiguous names are
      withheld from `synonym` on purpose and routed to the conflict view.

  (b) entity.obsolete, previously hardcoded 0 -- the mapping TSVs carry no
      dead signal, the history files do. Also inserts 1,324 accessions that
      appear in history but not in the current mapping files, so a conflict page
      can render whichever side is no longer current.

      UNEXPECTED: loading those accessions recovered 4,760 associations.
      load_associations skips rows whose miRNA accession is missing from entity
      (the "dead mirnas" TODO); they were being dropped silently. association
      went 1,295,770 -> 1,300,530, evidence 17,906,906 -> 17,936,913.

CASE IS LOAD-BEARING. miRBase distinguishes a precursor from its mature product
by capitalisation alone -- hsa-mir-34b is the hairpin, hsa-miR-34b the mature
strand. Conflicts must be grouped WITHIN a reference_level; casefolding a
combined list collapses the two namespaces and reports 24,768 false conflicts
instead of 274.

11.5 INDEXES, AND THE ONE THAT HAD TO COVER
--------------------------------------------
The built database had no indexes beyond UNIQUE autoindexes; the miRNA timeline
query measured 5.6s and association_evidence lookups scanned 17.9M rows. Six
indexes fixed it (schema/core.sql).

One is not obvious: ix_ae_assoc must be (association_id, sentence_id), not
association_id alone. The evidence view pages by DISTINCT sentence, and the
single-column index yields rowids that then need one random row fetch each to
read sentence_id -- 2.9s per page on the largest association. With sentence_id
in the index the page is an ordered range scan: 0.017s.

Also cached: the organism filter menu is an aggregate over all 1.3M associations
(0.32s) and was recomputed per page load. The database is opened immutable, so
it is computed once per process.

11.6 QUERY EXPANSION IS MAX, NEVER SUM
---------------------------------------
Searching a broad term joins ontology_closure to reach subtype associations.
Scores are aggregated with MAX and the matched descendants are shown as
"matched via". Summing descendant scores is the section 5.2 failure mode:
each is already log-compressed per term, so adding them inflates broad terms in
proportion to how many subtypes happen to co-occur. The UI labels this as query
expansion (5.1a), not the precomputed evidence propagation of 5.1b, which does
not exist yet.

ontology_closure holds STRICT ancestry -- ancestors() excludes self -- so a term
must be unioned with its descendants or its own associations disappear from its
own page.

11.7 EVIDENCE HIGHLIGHTING IS EXTENDED AT RENDER TIME
------------------------------------------------------
Term spans are stored correctly. miRNA spans are not: mir_regex.syn matches only
the stem, so 743,345 of ~794k stored miRNA spans are exactly 3 characters
('miR'), and the identifying digits live in a `suffix` field that never reaches
the database (analysis.py builds entity_positions as start + hit_length).
Highlighting the stored span renders "**miR**-26b-5p".

WORKAROUND: extend rightward over name characters, (?:[-\w*]|\.(?=\w))*, which
recovers the surface form from the sentence text. The lookahead on the dot
matters -- without it a sentence-final period is highlighted too. Validated over
1,816 spans: mean length 3 -> 8.7 chars, none malformed.

KNOWN LIMITATION: in an enumeration such as "miR-21, 221 and 16" three
normalized ids share one span, so all three extend to "miR-21". The correct fix
is threading `suffix` through CoOccurence -> .cooc -> loader; do it at the next
re-extraction, not before.

-----------------

12. AMENDMENT -- 2026-09-11: TAXON DROPPED FROM THE DATABASE, TWO STORAGE FIXES
================================================================================

12.1 TAXON IS NOT LOADED AT ALL -- completes the decision section 4 started
---------------------------------------------------------------------------
Section 4 excluded taxonomy from the closure because taxon is not an annotation
dimension: propagation up it terminates every association at "associated with
Eukaryota", which is no annotation content. But taxon ENTITIES and SYNONYMS were
still being loaded, which was the leftover inconsistency.

Measured against the built database, nothing referenced them:

  entity rows            2,854,488   (94.9% of the entity table)
  synonym rows           2,970,884   (94.2% of the synonym table)
  closure rows                   0
  search_name rows               0
  associations (either side)     0
  mir_mention_article rows       0

Taxa ARE load-bearing -- NormalizationContext.get_taxon_relevance() decides which
species prefix a bare 'mir-21' resolves to -- but that runs at EXTRACTION time,
reading the synonym files from disk, upstream of this database. By the time .norm
exists the species is already baked into the accession. atlas.db never consults it.

DECISION: skip HitType.TAXON when loading ontology graphs in build_db.py. One
exclusion suffices, because load_entities, load_synonyms and load_ontology_closure
all iterate `ontology_graphs`; no loader needed changing.

  entity   3,006,860 -> 152,372
  synonym  3,153,193 -> 182,309
  file          2.44 GB -> 1.75 GB
  build         17 min -> 16 min (the taxonomy .pkl alone was 27.5s of a 29s
                graph load; entity+synonym loading went 42s -> 2s)

The organism dimension is unaffected: entity.organism is derived from the miRBase
accession prefix, not from taxon hits. If a taxonomic rollup is ever wanted,
section 4 already specifies a curated ~30-row table.

12.2 mir_mention_article IS WITHOUT ROWID
------------------------------------------
A composite PRIMARY KEY on a rowid table builds a SEPARATE unique index
duplicating both key columns, so the data is stored twice. Measured: 83.7MB table
plus a 90.5MB autoindex -- the index LARGER than the table -- and every query read
the index (EXPLAIN showed USING COVERING INDEX), never the table.

WITHOUT ROWID stores the rows once, in the primary-key b-tree itself: 174.2MB ->
78.7MB. Row content and the uniqueness guarantee are unchanged; verified the
rebuild reproduces exactly 3,694,133 pairs.

This is the right shape for any pure junction table whose primary key is its whole
identity and whose payload is small.

12.3 ix_entity_type_org REMOVED
--------------------------------
Added on the assumption that organism filtering needs an index. EXPLAIN QUERY PLAN
on all four main queries never chose it: filtering always reaches `entity` by
rowid from `association` and then tests the column, so the index is never the
access path. 49.9MB. The schema now carries a comment recording why it is absent.

12.4 NEW FINDING -- 1-CHARACTER TERM SPANS (upstream, not fixed)
-----------------------------------------------------------------
0.56% of evidence rows (99,560 of 17,936,913) have a term span exactly one
character long -- a single letter or digit matched as an ontology term. They
resolve overwhelmingly to ontology ROOTS:

  '2' -> disease (MONDO_0000001)   5,417      'A' -> cell (CL_0000000)     2,892
  'A' -> transport (GO_0006810)    2,255      'A' -> pathway (PW_0000001)  1,587

Related: 'AD' (72,041 rows) and 'PD' (37,791) resolve to the generic `disease`
root rather than to Alzheimer's and Parkinson's disease.

This is a synonym/abbreviation-resolution defect upstream of the database; the UI
renders faithfully what the pipeline produced. Two things follow. First, the
associations built on these rows are junk. Second, they concentrate on exactly the
least informative terms -- which is what section 5.3's IC-ratio decay is designed
to zero out, since the root has IC=0 by construction. Implementing propagation
(Stage 4) would suppress their score contribution without special-casing anything.

NOTE FOR THE CHECKER: 2-character term spans are NOT anomalous. They are real
ABBREVIATION synonyms and account for 7.9% of evidence -- GC gastric cancer, OA
osteoarthritis, BC breast cancer, MI myocardial infarction, RA rheumatoid
arthritis, OS osteosarcoma. Only length 1 is suspect.

12.5 OBSERVED -- INDEXES ARE BUILT DURING LOAD, NOT AFTER
----------------------------------------------------------
The CREATE INDEX statements live in schema.sql, so every index exists while the
bulk load runs and is maintained per insert. Building one afterwards over sorted
data packs denser: ix_ae_assoc is 315.7MB when built during the load against
278.3MB when dropped and recreated on the finished table. Moving the CREATE INDEX
statements into build_db.py after the loaders would recover ~37MB and probably
some of the 8-minute corpus stage, which inserts 17.9M rows. Not done.

13.4 COLLISION POLICY -- DECIDED 2026-09-14 (supersedes the 2026-09-13 draft)
------------------------------------------------------------------------------
GOAL: keep refresh_data.py fully automatic. No hand-curated owner tables that a
new ontology release can invalidate. Some precision is traded for that, and the
trade is stated in the methods.

WHERE MENTIONS ARE LOST TODAY. _resolve_groups removes ABBREVIATION-typed hits
(from *_abbreviations.syn) from a group unless their id is supported by an
unambiguous mention in the same article. Hence:
  standard x standard         -> both survive -> AMBIGUOUS_ENTITY_TYPE, mention
                                 dropped (186,991 groups in the 2026-09-08 run).
  standard x abbreviation     -> standard side wins unless the abbreviation is
                                 supported; context-aware already (pig, MRSA, let).
  abbreviation x abbreviation -> only supported ids survive (COP).
Trap: acronyms the source ontology did not tag as ABBREVIATION sit in the standard
files and beat tagged ones. cl.syn has PD (pyloric dilator neuron, CL_4070015),
LC, FS, ICC, cDC as plain synonyms; an article that says "PD" without spelling
out Parkinson's disease resolves the mention to the crustacean neuron.

DECISION 1 -- EMIT ONE HIT PER TYPE (covers cl x bto, pw x go, polysemy).
  A same-span group holding several entity types is split by type; each part goes
  through the existing single-type resolution (exact / article support / LCA).
  AMBIGUOUS_ENTITY_TYPE disappears; give split groups their own status so the
  count can be reported.
  Why not exclude BTO's cell types instead: exclusion by collision with cl.syn
  removes 258 BTO nodes, but 82 of them have 167 descendants that stay (e.g.
  pluripotent stem cell -> adult stem cell, hematopoietic cell -> T-lymphoblast),
  so LCA fallback and propagation still reach excluded nodes, and many surviving
  descendants are cell types that simply share no string with CL (T-lymphoblast,
  astroglial cell). The hard rule is leaky and adds patches to LCA and
  propagation. Why not hand-curated owners for polysemy: every ontology release
  can add collisions, which would block automated refreshes.
  Justification for cl x bto: BTO's own top term is BTO:0000000 "tissues, cell
  types and enzyme sources" -- cell types are in BTO's scope by design, so a cell
  type appearing in both facets reflects the ontologies, not a modification.
  EXCEPTION -- groups containing a MIR hit keep today's behaviour
  (_prefer_contextual_mir). Every association hangs off a miRNA; a false MIR hit
  ("bantam" without miRNA context) costs more than a false term hit.
  CONSTRAINT -- no score may sum associations across term types. One mention can
  now back associations in two facets.

DECISION 2 -- FLAG, DON'T EXCLUDE, CROSS-ONTOLOGY CELL TYPES.
  Expected cost of decision 1: the CL terms that collide with BTO carried 67% of
  CELL associations in the 2026-09-11 build (104,160 of 155,172), so TISSUE
  rankings would be topped by fibroblast/neuron/endothelial cell. At DB build,
  compute a flag on TISSUE entities that share a surface form with a CL entity
  (computed, never curated). UI hides flagged terms in the TISSUE facet by
  default; evaluation reports tissue results with and without them.

DECISION 3 -- ACRONYM SHAPE HEURISTIC AT EXTRACTION.  [IMPLEMENTED, N = 8, see 15.2]
  A synonym tagged ABBREVIATION by the source ontology goes to the abbreviation
  file as today. Otherwise, if its DICTIONARY string (text casing never reaches
  us; syngrep is case-insensitive) has no whitespace, length <= N, >= 2 uppercase
  letters and uppercase >= half of its letters, it also goes to the abbreviation
  file. Same rule for every ontology. Removes the untagged-acronym collisions
  (PD, LC, FS, ICC, cDC, MAD) without curation.
  Flagged in the current standard files:
    N=5: disease 128, CL 80, GO 38, PW 0   (IDDM, SSc, AFib, NSC, PMN, RBC, EMT,
                                             BER, NER, MMR, NHEJ)
    N=8: disease 244, CL 98, GO 45, PW 0   (+ CMS-TA, CFU-EM, TC-NER, OXPHOS)
  Mixed-case forms (VFib, EndMT, cvEDS) are flagged on purpose.
  COST IS RECALL: a reclassified synonym only survives where the article supports
  it (full name elsewhere, or an inferred "(EMT)" definition). GO's abbreviation
  file is empty today, so EMT/NHEJ/OXPHOS are currently exact matches.
  OPEN: choose N from the per-synonym group-status counts the processor already
  logs (EXACT_MATCH -> RESOLVED/FAILURE for flagged strings) in the next run.

DECISION 4 -- COLLISION MATRIX IS A REPORT, NOT A GATE.
  refresh_data.py logs the matrix and the collisions new since the last refresh.
  It never fails on them.

OPEN -- MONDO SYNONYM ERRORS (disease x bto_NEW).
  Not a collision problem: MONDO lists organs as exact synonyms of inflammation
  terms (epididymitis <- epididymis, hypophysitis <- hypophysis, panniculitis <-
  Subcutaneous tissue, ...). They create wrong disease hits with or without BTO,
  and decision 1 does not fix the disease hit. 6-8 strings. Either document, or
  add an automatic rule "drop a DISEASE synonym identical to a TISSUE term name"
  (DISEASE extraction then depends on bto.syn).

REJECTED: single global type order (SIV and anthrax are one pair with opposite
answers); hand-curated owner tables (block automation); hard exclusion of BTO
cell types (leaky, see decision 1); context-based type disambiguation (needs an
annotated evaluation set); status quo (losses are invisible in the outputs and
concentrate on high-value terms, e.g. Wnt signaling pathway 29,728).

14.4 IC THRESHOLD -- WHERE IT IS APPLIED (amends 13.1)
------------------------------------------------------
DECISION: filter at DB LOAD. Not at hit / normalization level, not only at query
time.
  At build: associations (direct and propagated) whose term is below the cutoff
  are not loaded, their association_evidence rows are skipped, and only
  still-referenced sentences are inserted. entity and ontology_closure rows for
  general terms are kept, so query expansion from a general term's page still
  works. The cutoff is recorded in build provenance. Changing it costs a DB
  rebuild (~16 min), not a re-extraction.
Why not at hit level (the original idea behind keeping NormalizedHit.score):
  - For surviving associations the scores WOULD be identical (a hit below the
    cutoff only feeds terms that are even more general), but
  - ENTITIES_PER_SENTENCE_CAP counts distinct spans over all normalized hits in
    Grouper.extract_cooccurrences; removing general hits first changes which
    sentences pass the cap and therefore the scores of specific terms;
  - every cutoff would need a full re-extraction (~81 min), and the cutoff is
    meant to be chosen from the distribution of associated terms, which does not
    exist yet at hit level;
  - filtered hits vanish from .norm (12.4 junk analysis, recall checks);
  - the per-hit IC is stale anyway (14.2).
Why not only at query time: ~10% of the file is direct evidence on root-level
terms (14.3).
Observations for choosing the cutoff:
  - Natural gap: below 0.05 is roots only, 0.05-0.15 adds almost nothing
    (38.4k -> 40.0k associations). Any cutoff in that range means "remove roots"
    and is insensitive to the exact value.
  - Above 0.15 terms that are not obviously uninformative start to go: neoplasm
    0.19, neuron 0.17, epithelial cell 0.19. CL values are low overall, so a single
    global cutoff may treat ontologies differently. OPEN: global vs per-ontology.

exactly 2,583 standard synonyms: extraction keeps EXACT-scope synonyms only, and
BTO's synonyms are RELATED (e.g. "Koerper" on whole body). Tissue recall rests on
exact term names. OPEN: whether to admit RELATED synonyms for BTO (they include
foreign-language forms, so not wholesale).

15.2 ABBREVIATION HEURISTIC (implements 13.4 decision 3)
--------------------------------------------------------
get_exact_synonyms puts an EXACT synonym into the abbreviation list if the
ontology tags it ABBREVIATION (unchanged), OR if probable_abbreviation(text)
holds and the text is not the term's own name:
    no space, len <= 8, >= 2 uppercase letters, uppercase >= 50% of LETTERS
Case is read from the dictionary string; syngrep matches case-insensitively, so
text casing never reaches the rule.

Choice of rule, evaluated against the 5,691 ontology-tagged abbreviations with an
uppercase letter (disease + cell abbreviation files):
  rule                                  recall tagged   flagged (dis/CL/GO/PW)  names
  len<=5, >=2 upper, upper>=50%             75.3%        128 / 80 / 38 / 0       11
  len<=8, same  (CHOSEN)                    97.4%        244 / 98 / 45 / 0       17
  len<=10, same                             98.0%        287 / 113 / 45 / 0      18
  len<=8, no lowercase run >= 3             97.3%        228 / 97 / 44 / 0       15
  all letters uppercase, len<=8             96.1%        115 / 65 / 37 / 0       10
  - Mixed case is kept on purpose: pDC, cDC, SSc, vCJD, EoE, aHUS are genuine
    acronyms and include the pDC/cDC-type CL collisions.
  - Denominator is letters, not len(): len() loses 22q11DS, EBS-loc, TSH-oma,
    bHLHa26 (disease) and DC.4+, DC.8+, NK.sp, he-NK, T.DN4.th (CL).
  - Term names are never reclassified (AIDS, COVID-19, PANDAS, VIPoma, GRFoma,
    ILC1, ...): as abbreviations they would only count with article support; in a
    46% post-2020 corpus that alone would cost COVID-19 recall.
  - Not caught, accepted: word-like or gene-style tagged forms (Gla, Arts, Norse,
    Chac, Sca1) and forms with spaces (MPS I, ML IV). A shape rule cannot tell
    them from words; they are tagged anyway.

Result on the current graphs (extract_synonyms):
  type        standard synonyms   tagged   heuristic   abbreviations after
  disease          85,366          5,737      232           5,969
  cell              6,094             15       93             108
  GO-BP            71,934              0       45              45
  tissue            2,583              0        0               0
  pathway           3,122              0        0               0
Candidate lists: outputs/abbreviation_candidates_<type>.tsv (term_id, synonym,
term_name); identical to the heuristic's output.

Effect on resolution: a reclassified synonym is accepted only with article
support (unambiguous mention elsewhere, or an inferred "(EMT)" definition);
otherwise FAILURE. Collision acronyms now arbitrated by article evidence instead
of the standard side winning: PD, LC, FS, ICC, cDC (disease x CL), MAD (disease x
GO), PMN (CL x GO). "PD" no longer resolves to the crustacean pyloric dilator
neuron by default. COP was already tagged on both sides.
COST: recall for acronyms used without definition. GO is most exposed (EMT, NHEJ,
OXPHOS move from always-accepted to article-dependent). Measure with the sample
run: group statuses of the 370 reclassified strings.

Known, pre-existing: 8 disease synonyms are in both lists (IgAD1, CGF1, AIDS,
CADDS, ...). MONDO itself TAGS these term names as ABBREVIATION, and
extract_synonyms also adds every name as standard. Harmless in resolution (same
id, standard survives). Optional cleanup: apply the name exception to tagged
synonyms too.
Not done: an audit TSV written by refresh_data.py (get_exact_synonyms does not
report why a synonym is an abbreviation); unit tests for probable_abbreviation.
Correction to an earlier review: scripts/ontology/create_obo_import.py defines its
own get_exact_synonyms and is not affected.
